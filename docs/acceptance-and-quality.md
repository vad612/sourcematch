# Приёмка и оценка качества

## Условия приёмки

| Что проверяется | Как проверяется |
| --- | --- |
| Воспроизводимость | Проверяющий запускает решение одной командой по инструкции и получает `submission.csv` из исходных материалов. Запуск на новой выгрузке — обязательное условие дальнейшей оценки |
| Полнота и формат | В файле одна строка на каждый `listing_id` из шаблона. Поля и допустимые значения соответствуют [формату результата](business-requirements.md#формат-результата) |
| Решения о закупке | Ответы по 3 700 карточкам сравниваются с ответами заказчика по таблице стоимости ошибок |
| Подбор предложений | Среди размеченных карточек с аналогами измеряем долю тех, у которых хотя бы один эталонный аналог попал в первые три предложения. Отдельно измеряем долю верных `NONE` среди карточек без аналогов |
| Экономика | На примерах с достаточными данными независимо рассчитываем эталонную маржу по правилам закупки и расходов. Считаем среднее абсолютное отклонение в UZS и отдельно долю проверенных карточек, для которых выдана числовая маржа. В переданной разметке эталонных значений маржи нет |
| Ручная проверка | Из спорного случая должно быть понятно, почему решение передано человеку, что ему нужно проверить и что произойдёт с внесённым исправлением |
| Неопределённость | Проверяющий оценивает, видно ли, когда неизвестный вес или другие недостающие данные мешают сделать уверенный вывод |
| Новая выгрузка | На защите заказчик уберёт поле оценки спроса, изменит валютный курс и добавит категорию с сертификацией. Он проверит, где отразятся изменения и как будет восстановлена работа. Отдельно оценивается, насколько легко подключить вторую страну |

## Стоимость ошибок

| Ответ | Эталон `брать` | Эталон `не брать` |
| --- | ---: | ---: |
| `брать` | 0 | −5 |
| `не брать` | −1 | 0 |
| `проверить вручную` | −0,3 | −0,3 |

Пустой ответ приравнивается к ручной проверке. Ложный запуск штрафуется в пять раз сильнее пропущенного товара. Ручная проверка расходует время команды, поэтому при оценке важно видеть её долю вместе с ошибками обоих типов.

## Свидетельства качества

До сдачи нужно указать, на каких данных проверено решение, какие метрики получены и какие типы ошибок обнаружены. Размеченные карточки позволяют проверить решения и причины, подходящие предложения и случаи без аналога. Для проверки экономики нужны случаи с исходными данными, достаточными, чтобы заново получить ожидаемые суммы по правилам. В отчёте нужно показать конкретные записи с выявленными проблемами данных и описать, как каждая проблема была учтена.

При сверке правил проверяем приоритет причин, случаи неполных данных и граничные значения.

| Случай | Ожидаемый результат |
| --- | --- |
| Есть несколько подтверждённых оснований для отказа | `не брать`, код первого подтверждённого нарушения по порядку из правил экономики |
| Оценки спроса по разные стороны порога и подтверждённой причины для отказа нет | `проверить вручную`, причина начинается с `LOW_DEMAND`, если предыдущие условия подтверждены |
| Данных о весе или упаковке недостаточно для устойчивого расчёта | Затронутые денежные поля пустые. Если нет подтверждённой причины для отказа, карточка передаётся на ручную проверку |
| Минимальная партия ровно 1 000 единиц, маржа ровно 18%, подтверждённый спрос ровно 60 заказов | Соответствующие условия проходят пороги |
| Упаковка ровно 0,6, 5 или 37 л | 0,6 л относится ко второму тарифу, 5 и 37 л — к третьему |
| Карточка продаёт набор | Себестоимость и маржа рассчитаны на весь набор, лимит партии проверяется в наборах |

ТЗ требует объяснить, как в ежедневной работе команда узнает об ухудшении качества при смене формата выгрузки, снижении надёжности источника спроса, изменении курса или появлении новой категории. Также нужно показать, что текст продавца не может менять бизнес-правила и управлять решением.

На защите предусмотрено 60 минут. Из них 10 отведены на показ результата, 20 — на вторую выгрузку с изменёнными условиями, 20 — на разбор десяти случайных ошибок и 10 — на вопросы кандидата.

## Комплект сдачи

- Воспроизводимое решение в репозитории или архиве с инструкцией запуска и заполненный `submission.csv`.
- Отчёт до шести страниц в PDF, HTML или Markdown. В нём нужны обоснование способа работы на каждом шаге, стоимость и время прогона на 1 000 карточек, результаты проверки, контроль качества и разбор проблем данных. Если на каком-то шаге отказались от LLM, нужно объяснить почему.
- Записка «первые 90 дней» до двух страниц. В ней нужны пять вопросов сорсеру и аналитику и последствия ответов, работа человека со спорными случаями и его исправлениями, один измеримый результат к 90-му дню, границы автоматизации и следующий этап выхода на рынок.
- При использовании ИИ нужны полная история диалогов, `context.md` с описанием переданных материалов и их порядка, названия модели и инструмента, а также перечень замеченных ошибок ИИ и исправлений.

Источник критериев — [текст задания](../input/task%20%281%29.html). Метрики подбора и маржи здесь приняты для собственной проверки. Заказчик оценивает эти показатели отдельно, его формулы и пороги в ТЗ не указаны.
