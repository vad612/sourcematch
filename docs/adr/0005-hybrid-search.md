# ADR 0005. Гибридный поиск в LanceDB

## Контекст

Векторный канал способен найти переводы и перефразы. Для идентичных артикулов, размеров и коротких серий полезен независимый лексический канал. Поиск должен работать в процессе CLI.

## Решение

Используем встроенную LanceDB и Arrow. В таблицах предложений и каталога храним стабильный ID, текстовые ключи, вектор и ссылки на нормализованные записи. LanceDB выполняет поиск по косинусному сходству, BM25 и объединение RRF через адаптер модуля. На корпусе из 9 704 предложений начинаем с точного векторного поиска и полнотекстового индекса для лексического канала. Переход к приближённому поиску зависит от измерений и проверки потери полноты относительно точного поиска. [LanceDB Rust](https://docs.rs/lancedb/latest/lancedb/), [VectorQuery](https://docs.rs/lancedb/latest/lancedb/query/struct.VectorQuery.html), [RRFReranker](https://docs.rs/lancedb/latest/lancedb/rerankers/rrf/index.html)

## Запрос и выдача

- Для BM25 используем FTS с символьными 2–3-граммами по очищенному заголовку и строкам из нормализованных признаков. Это покрывает китайские токены без пробелов. Серии и числовые признаки также передаём модулю проверки отдельно. Запрос формируем типизированным `MatchQuery` с явной колонкой. Исходный текст передаётся как значение запроса. [FtsIndexBuilder](https://docs.rs/lancedb/latest/lancedb/index/scalar/struct.FtsIndexBuilder.html), [Lance MatchQuery](https://lance.org/guide/full_text_search/)
- Категория продавца может увеличить релевантность, но не исключает предложения. Без текстового сигнала используем имеющиеся точные признаки. Если данных недостаточно для обоих каналов и точного поиска, отмечаем неполное покрытие.
- Начальный и расширенный объёмы выдачи задаются профилем. Расширение запускаем в рамках общего бюджета, когда первый поиск даёт пустой результат, неоднозначное совпадение или только аналоги с непригодной партией. Если подтверждён составной ключ модели, добавляем предложения по нему независимо от ранга. Само совпадение ключа проверяется по определяющим признакам.
- `CandidateSet` содержит стабильные ID, позиции в каналах, RRF, способ поиска, причину расширения и признак покрытия. Адаптер LanceDB объединяет каналы встроенным RRF. Реранжирование получает часть выдачи отдельно. Стабильный ID разрешает равенство. Пустая лексическая выдача при доступных других сигналах считается штатной. [Интерфейс объединения LanceDB](https://docs.rs/lancedb/latest/lancedb/rerankers/trait.Reranker.html), [ADR реранжирования](0015-reranking.md)
- Строим индекс по хешу документов, упорядоченных по ID, профилю модели, схеме и токенизатору. Данные закупки и логистики подгружаем по ID из текущей выгрузки, включая при совпадении поискового кеша. Поисковые хеши не зависят от курса и других ставок. Один адаптер обслуживает отдельные таблицы предложений и каталога.

## Проверка и компромиссы

Сравниваем векторный, BM25 и гибридный режимы на одинаковых группах карточек. Меряем попадание хотя бы одного эталонного аналога, полноту всех размеченных аналогов и наличие самого дешёвого пригодного предложения там, где оно известно. Смотрим чувствительность к изменению объёма выдачи и времени. Отдельно проверяем смену языка, добавление нерелевантных и дублирующих предложений и смену порядка строк. При высокой стоимости поиска сравниваем другие готовые индексы по полноте, времени и нагрузке.
